# Wan 2.2 14B roadmap

Last reviewed: **2026-08-11**  
Target workstation: **Windows 11, RTX 5080 16 GB (SM120), Python 3.12**

## Executive decision

Wan 2.2 14B is not one generic checkpoint. Its A14B video lines use a two-expert
Mixture-of-Experts denoising topology:

1. a **high-noise expert** for the early denoising stage;
2. a **low-noise expert** for the later stage;
3. separate official model lines for **T2V** and **I2V**.

Engine currently implements only **I2V**, through an exact five-resource Comfy-aligned
stored-FP8 closure. That path is the correct near-term product candidate, but it is not
yet Recommended: target-workstation output/cancellation/reuse acceptance remains
incomplete. The support-only directory is now an automatically acquirable, immutable
12-file Hugging Face whitelist; its artifact and topology still require acceptance.

Do not broaden into T2V, first/last-frame, community acceleration LoRAs, or additional
quantized formats until the current I2V path is reproducible and accepted. The small
ladder is matching dense BF16 I2V as reference, the current exact scaled-FP8 I2V path
as challenger/incumbent, and no second quantization format yet.

## Evidence labels

- **Verified** — stated by Wan, Comfy, or the Engine source/catalog at the audited
  commit.
- **Publisher measurement** — an upstream speed/memory claim, not an Engine result.
- **Inference** — a roadmap product judgment requiring target-workstation validation.

## Scope and lineage boundaries

| Line | Operation | Upstream topology | Engine state | Comparison boundary |
| --- | --- | --- | --- | --- |
| Wan 2.2 T2V-A14B | Text-to-video | High-noise + low-noise 14B experts, UMT5, VAE, scheduler/tokenizer support | Not implemented | Separate BF16/FP8 T2V ladder if product demand is later established |
| Wan 2.2 I2V-A14B | Image-to-video | High-noise + low-noise 14B experts, UMT5, Wan 2.1 VAE, I2V support/config | Exact Engine path exists | Current roadmap priority |
| First/last-frame or other control variants | Additional conditioning or community workflows | Not the same official operation contract | Not implemented | Separate future line; never infer from ordinary I2V |

Wan's official model card describes A14B as a roughly 27B total MoE with about 14B
active parameters per denoising step, supporting 480p and 720p. The model weights are
Apache-2.0. Verified sources:
[official Wan2.2 code](https://github.com/Wan-Video/Wan2.2/tree/42bf4cfaa384bc21833865abc2f9e6c0e67233dc),
[official I2V-A14B model card](https://huggingface.co/Wan-AI/Wan2.2-I2V-A14B), and
[official I2V Diffusers repository](https://huggingface.co/Wan-AI/Wan2.2-I2V-A14B-Diffusers).

## Official Comfy topology and settings

The official Comfy I2V example uses:

- `wan2.2_i2v_high_noise_14B_fp8_scaled.safetensors`;
- `wan2.2_i2v_low_noise_14B_fp8_scaled.safetensors`;
- scaled-FP8 UMT5-XXL;
- `wan_2.1_vae.safetensors`;
- 20 steps split at step 10;
- CFG 3.5 for both stages;
- Euler sampler, `simple` scheduler, and model-sampling shift 8.

Pinned implementation reference:
[`image_to_video_wan22_14B.json`](https://github.com/comfyanonymous/ComfyUI_examples/blob/master/wan22/image_to_video_wan22_14B.json).
The `master` branch is mutable and must be pinned before implementation changes.

The companion official Comfy T2V example uses the same two-stage pattern with T2V-
specific expert files:
[`text_to_video_wan22_14B.json`](https://github.com/comfyanonymous/ComfyUI_examples/blob/master/wan22/text_to_video_wan22_14B.json).
It is evidence that T2V is real, not evidence that Engine's I2V adapter can load it.

### Frame-rate source conflict

Wan's official model documentation describes 24 fps output. An older official Comfy
example JSON sets its save node to 16 fps. Engine deliberately uses 24 fps. Treat this
as an unresolved source conflict until the exact current official workflow/template is
pinned and the intended playback rate is confirmed. Do not silently change the model
operation or “correct” timing after generation.

## Current Engine truth at `2ba5709`

- **Package-owned I2V recipe exists:**
  [`wan-2-2-14b-i2v-image-to-video-comfy-org-fp8.toml`](https://github.com/EnviralDesign/LatentSlate-Engine/blob/2ba57095796ca6e13285afd23da3582383d82df9/src/latentslate_engine/builtin_recipes/wan22/wan-2-2-14b-i2v-image-to-video-comfy-org-fp8.toml).
- **Native stored-weight runtime exists:**
  [`tools/wan22_native.py`](https://github.com/EnviralDesign/LatentSlate-Engine/blob/2ba57095796ca6e13285afd23da3582383d82df9/src/latentslate_engine/tools/wan22_native.py)
  and the associated runtime implement I2V only, without runtime weight conversion.
- **Default Engine operation:** 24 fps, 81 frames, 832×480, 20 steps, high/low CFG
  3.5, and a validated stage split. Cancellation/failure is designed to eject model
  state rather than reuse a poisoned session.
- **Acquisition is exact and remote provisionable.** The support declaration pins the
  official revision and enumerates 12 exact `allow_patterns`, whose aggregate is
  529,069,044 bytes. The whitelist includes only the required configs/tokenizer,
  `README.md`, and the official Diffusers VAE; no transformer or text-encoder weight
  path can be selected.
- **Proof level:** stored-weight I2V runtime/workstation path is reported proven, but
  package install is local-only and the planned output/cancel/reuse acceptance matrix
  remains incomplete. Do not conflate “one job ran” with Recommended.
- **T2V and first/last are absent.** No native Engine recipe/runtime exists for those
  operations.

## Small qualification ladder

### I2V

1. **Reference:** exact official dense BF16 I2V-A14B repository, 20 steps, fixed
   high/low boundary, CFG, source image, seed, dimensions, frames, and 24 fps.
2. **Incumbent/challenger:** the current exact five-resource stored-FP8 Engine path with
   the same operation settings.
3. **Optional experiment:** none until the FP8 path is accepted.

The BF16 reference may require more host RAM/offload than is product-viable; it still
must be retained for output comparison. A reference is not automatically the default.

### T2V

Deferred. When product demand exists, create a separate BF16 versus official Comfy FP8
ladder using T2V-specific high/low experts. Never reuse an I2V transformer contract.

## Model-specific acceptance

Use the shared harness in [README](./README.md), plus an I2V corpus covering:

- people, faces, full-body articulation, animals, vehicles, products, landscapes, and
  stylized illustration;
- static camera, pan, tilt, dolly, orbit, handheld, and subject-driven motion;
- low-motion and high-motion prompts, source-image text/signage, fine texture, and
  occlusion/reappearance;
- 480p and 720p-class buckets, 81 and 121 frames, with playback fixed at 24 fps;
- prompt adherence versus source-image fidelity, first-frame reconstruction, identity,
  anatomy, motion smoothness, temporal texture, and camera realism.

Record source-image preprocessing, UMT5 encode/cache, high-expert load and steps,
stage boundary/ejection, low-expert load and steps, VAE decode, mux/export, peak
VRAM/RAM, disk reads, and host-device transfer. Exercise cancellation during each
expert load, each denoising stage, the stage transition, VAE decode, and export; then
run a clean follow-up job.

Measure warm reuse both with and without reusing the same source/prompt. A session that
keeps both 14B experts or stale latent state in memory is a failure even if the first
job succeeds.

## Hard gaps and unresolved source conflicts

1. **Output acceptance gap:** target-class generated outputs, cold/warm timing, peak
   memory, cancellation, and repeated-job health are not fully recorded.
2. **Frame-rate conflict:** official Wan documentation says 24 fps; an older official
   Comfy example saves at 16 fps. Resolve with a pinned current template and explicit
   product decision.
3. **Reference feasibility:** dense BF16 may not be practical on 16 GB, but no quantized
   output can be accepted without a matching I2V reference somewhere in the harness.
4. **Stage topology is semantic:** high and low experts are not interchangeable files,
   and the stage boundary is part of the recipe.
5. **T2V is separate:** official T2V artifacts exist, but Engine's I2V proof says
   nothing about T2V loading, outputs, or lifecycle.

## Ordered next actions

1. Exercise the exact remote five-resource installation and retain its immutable
   deployment lock before hardware acceptance.
2. Pin the current official Comfy I2V workflow/template revision and resolve the
   16-versus-24-fps conflict.
3. Run the current five-resource recipe through the fixed I2V corpus and record every
   stage, dispatch, cold/warm, memory, cancel, reuse, and teardown result.
4. Establish the dense BF16 reference on suitable hardware/offload and review paired
   output quality without changing the operation settings.
5. Fix any stale-session or stage-ejection defects before optimizing speed.
6. Promote the FP8 path only after material creator-value gates
   pass.
7. Start a separate T2V roadmap line only after I2V is stable and product demand is
   explicit.

## Explicit non-goals

- Do not merge T2V and I2V artifacts or acceptance results.
- Do not treat one 14B expert as a complete model.
- Do not add more quantization formats before the exact FP8 path is installable and
  accepted.
- Do not rebuild or quantize official weights at Engine runtime.
- Do not claim 16 fps and 24 fps outputs are equivalent.
- Do not call local manual artifact presence a reproducible deployment lock.
